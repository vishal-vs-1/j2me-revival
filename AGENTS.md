# Repository work rules

- Never commit, push, stage, or publish changes unless Vishal explicitly asks in the current conversation. Keep implementation and experiment artifacts local until then.
- Preserve user data and unrelated work. Do not reset, stash, clean, or bulk-delete the workspace without Vishal's explicit authorization. Do not inspect or modify `gamesss/` unless the user asks.
- Before an authorized reset, restore, or similar action that would discard local changes, create a named Git stash containing the affected tracked and untracked work and verify that it contains those changes. Keep saves, captures, and local history outside the cleanup scope. If the stash cannot be created or verified, stop before discarding work.
- Keep changes focused and follow SOLID: one clear responsibility per class/module, inject dependencies at boundaries, and avoid game-title-specific branches in shared code.
- Keep normal gameplay paths unchanged unless a task explicitly requires a guarded integration. Optional capture/analysis must be disabled by default, bounded, and fail closed.
- Ask before controlling the user's desktop, opening or interacting with their apps, or relying on live computer state. Repository and test-fixture inspection does not require desktop access.
- Put comments immediately above non-obvious logic and invariants. Prefer short comments that explain why; do not narrate each statement.
- Keep local designs, task lists, experiment results, reviews and history in ignored `local-work/`. Start with `local-work/README.md` and `local-work/STEPS.md`; the 2.5D designs/tasks are in `local-work/scene25d/`. Build products and temporary focused-check outputs may stay in `build/`; game captures stay in their existing per-game workspace. Do not add personal or game-derived data to source control.
- Preserve `local-work/` permanently. Never remove it during cleanup, packaging or release preparation, and never replace old history with a shorter summary. Append corrections and new results. Moving its contents requires preserving files and updating the relocation map and live references. Historical results may name their original paths; consult `local-work/RELOCATIONS.json`.
- For every meaningful implementation, investigation or experiment step, append a dated entry to `local-work/STEPS.md`: a short title and exactly two simple sentences on separate lines, one saying what was tried and one saying what happened or remains unknown. Use everyday language, explain unavoidable jargon, and never claim a failed or unmeasured trial succeeded. Update it before ending the turn, including blocked or unsuccessful attempts.
- Keep the detailed record in `local-work/history/PROJECT_HISTORY.md`. After an implementation is validated and finalized, update the relevant HLD and LLD plus task status. Keep unverified findings labeled as experimental rather than product guarantees. Do not ask for another game recording until existing saved evidence has been traced to a concrete missing input or a repaired collector has passed focused checks.
- Run only focused checks needed for the requested change. Report what changed, evidence, limitations, and any required user action.
